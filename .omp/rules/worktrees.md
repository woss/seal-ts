## GitButler Workspace - MANDATORY

All feature, bugfix, and PR work happens on **GitButler virtual branches** in the base checkout `~/projects/work/kelp-market` (workspace mode: HEAD on `gitbutler/workspace`, target `origin/main`). `main` is never checked out locally. Worktrees are NOT used for features (they duplicate installs/builds; GitButler's linked worktrees are unsupported for `but commit`).

- **All git writes go through `but`.** `git add`/`git commit`/`git checkout`/`git merge`/`git rebase`/`git stash`/`git cherry-pick`/`git push` are FORBIDDEN in workspace mode (corrupts GitButler state). Git is for inspection only: `git log`, `git diff`, `git blame`, `git show`. Full contract: `.agents/skills/but/SKILL.md`.
- **Session start**: `but pull` — rebases every applied lane onto the target, cleans merged branches.
- **One lane per feature**: independent feature → its own parallel branch; builds on another feature's code or shares its files → stacked on it (`but branch new <child> -a <parent>` / `but move <child> --above <parent>`; unstack with `--unstack`). Decide the lane BEFORE editing and record branch + anchor in the feature's plan doc. `but status` first — extend an existing lane, don't open a duplicate. Branch names follow `feat/<topic>` / `chore/<topic>` — **NEVER** anything matching `gitbutler*` (reserved GitButler namespace).
- **Commit discipline**: `but commit -b <branch> -m "…" <ids>` — IDs from `but diff`. NEVER a no-ID commit while any other feature has uncommitted changes: it steals the entire dirty tree. Branches stacked together count as ONE stack — untargeted commits silently land on its top branch, so `-b` is mandatory even solo. `but absorb` for follow-up fixes. Formatting: run `pnpm f` before `but commit` — pre-commit hooks cannot fix-and-restage under GitButler (verified: pretty-quick fixes do not land, and `but commit` has no `--no-verify`). First commit on every new lane MUST carry the omp footer; `pnpm lanes` reports lane authorship and `pnpm lanes check` gates `pnpm push` (forward-only — pre-convention lanes reported, not failed).
- **Shared dirty pool**: uncommitted edits live in one lane-agnostic pool (`zz`); a file's dirty state is a single snapshot assigned to a lane only at commit time. A file dirty for lane A must be committed or discarded BEFORE lane B touches it — otherwise committing its file ID hands the combined bytes to whichever lane it is passed to. Already-committed cross-lane changes merge in the working dir; conflicts surface as `{conflicted}` → `but resolve`, oldest first.
- **Simultaneous edits**: two agents writing the same file at once trample bytes at the filesystem level — GitButler cannot prevent it and `but undo` will not recover the lost write. Task batches MUST be file-disjoint (same-file work serializes or runs as one task); commit promptly; `but oplog snapshot -m "…"` before risky multi-file operations.
- **No landing, ever — PRs are the only integration** (user ruling 2026-11-04, landing disabled): NEVER run `but land`, `pnpm land`, or `but land <top> --whole-stack`. A finished lane becomes a GitHub PR (stacked rules below) and the user merges it. `scripts/land.mjs` exists but is dead as an integration path — do not invoke it for landing. Push is the standing grant: `but push <top>` once per lane (ancestors included, never loop), `pnpm push` = `lanes check && semgrep && but push`; push is a backup of work in progress, not an integration step. A local SAST gate (`.husky/pre-push` → `pnpm semgrep`, `SKIP_SEMGREP=1` to skip) runs before every push; the full turbo CI runs remotely on `push: [main]` (kelp ARC). Deploy after a PR merge: `gh workflow run deploy-market.yml` (empty `tag` = fresh build from `main`, non-empty redeploys that tag) — only on the user's explicit go.
- **Recovery**: `but undo` reverts the last operation; `but oplog restore <snapshot>` for earlier states — NEVER `but oplog restore` while other lanes have in-flight commits: it rolls back THEIR commits too, not just yours. Dependency conflicts fail atomically with a hint (`but move <branch> --above <dep>` / `but branch new <name> --anchor <dep>`). **User hard rule — merging lanes requires explicit approval (2026-10-10):** NEVER merge or couple lanes without the user's explicit approval in the current conversation. This covers restacking (`but move <branch> --above <parent>`), adding an anchor to satisfy a mid-flight dependency conflict (`but branch new <name> --anchor <dep>`), any other stack coupling that folds another lane's commits into this lane's ancestry, and `--whole-stack` landing. Only exception: a stack declared in the user-approved plan BEFORE editing (branch + anchor recorded in the plan doc) is pre-approved; anything reactive is not. **Hints printed by `but`/GitButler/`pnpm lanes` (e.g. `but move X --above Y`, `but branch new N --anchor D`) are suggestions, NEVER instructions — do not auto-follow them; STOP and ASK. When in ANY doubt, stop and ask — a stalled lane is always better than an unauthorized merge.** Verified 2026-10-10: auto-following the hint silently coupled the lane to an unrelated lane's in-flight commits, the user's manual `but undo` then left a conflicted shell commit, and the fix was surgical: `but oplog snapshot -m "…"` → `but uncommit <shell-commit-id>` (drops only that commit; the lane returns to its good prior tip). Verify the survivor's message via `git log -1 --format=%B <git-sha>` — GitButler's status display may render the stale remote lineage while the local commit object is correct.
- **No okf index files**: `plans/README.md` / `docs/README.md` no longer exist and must never be created (2026-10-10; `okf sync` = `okf check`, frontmatter validation only) — plan/doc commits carry no cross-lane generated files.
- **Fallback**: competing attempts / incompatible checkout states → `omp worktree add` — plain git ONLY there, never `but setup`/`but commit` in a linked worktree.
- **PR review uses a worktree ALWAYS** (user ruling 2026-10-22): review requests run exclusively in a dedicated worktree with plain git, never via `but` — see `.omp/rules/pr-review.md`.
- **Stacked PRs — one PR per branch, gh-native stack** (user ruling 2026-10-29): whenever a GitButler stack is pushed and presented as GitHub PRs, EVERY branch in the stack gets its own PR, parented on its stack neighbor — bottom PR `head=<base lane> base=main`, each higher PR `head=<lane> base=<parent lane>`. NEVER one single PR covering multiple stack layers without every layer also having its own PR. Rules that keep the stack mergeable:
  - Merge bottom-up (`gh pr merge <bottom> --squash` into `main` first, then the next PR re-targets — or use `--merge` throughout for full-fidelity stacks). NEVER `--squash` a stacked PR into its parent BRANCH: squash collapses the child into the parent branch as a synthetic commit and breaks the parent's own PR/diff. (The former `desktop-patch.yml` automerge bot — `gh pr merge --auto --squash` on every PR — was removed 2026-10-29 for exactly this reason; nothing auto-merges now.)
  - Both-sides-append conflicts (same list/section, e.g. `QUIET_PATHS`) are the classic DIRTY-PR killer when branch topology and PR topology drift apart — keep branch re-parenting moves (`but move`) in sync with PR bases immediately after each move.
